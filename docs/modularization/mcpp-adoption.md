# What Hermes can gain from mcpp, and what could break

**Recommendation for the workstream, 21 November 2026.** Give Usman's proposal the first trial. One command that builds and tests a real Hermes component on a fresh contributor machine would already be worth having. A second, more ambitious outcome is for mcpp to compile the host while the existing distribution recipes continue to install it. Replacing those recipes is a third decision with a different cost and audience.

This review uses [Hermes at 24f68ce](https://github.com/MrOz59/Hermes/tree/24f68ce730780a7fab5a9b1cc4b08a6f981ae554), [mcpp v2026.11.20.1](https://github.com/mcpp-community/mcpp/releases/tag/v2026.11.20.1) and the separately versioned [official plugins at v0.26.1](https://github.com/mcpp-community/mcpp-plugins/tree/v0.26.1). The observations below come from those sources. The proposed Hermes trials have not been run.

## Where the proposal has leverage

| Opportunity | First Hermes experiment | What would count as a gain |
| --- | --- | --- |
| A contributor can reproduce the compiler choice and diagnose a setup difference. | Have two contributors build the same routing revision on clean environments. Save the machine-readable output from `mcpp why toolchain --format json` and record manual setup, bytes downloaded and time to the first passing test. Compare against the focused CMake target. | Both obtain the expected test results and can explain any difference in compiler or sysroot from the recorded output. A faster second build and an easier first install are distinct benefits. ## Failure modes and how to detect them

**1. A locked build can detect drift and still be impossible to reconstruct.** At the pinned release, `--locked` checks the resolved graph against `mcpp.lock`. The upstream support document explicitly distinguishes verification from using the lock to select the entire resolution. `--offline` depends on already available inputs. A cold runner can therefore fail correctly while an old developer cache continues to work. Record the index revision, tool and plugin versions, SDK source and payloads along with the lock. Restore them into a *different* clean home, disable network access and repeat the build. Retain the original pins if a dependency refresh cannot reproduce the previous package. [Resolution contract](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/docs/51-supported-versions.md) · [Implementation of the lock check](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/src/build/prepare/records.cpp)

**2. Updating the build tool becomes a maintenance responsibility.** Upstream supports the newest release and describes a narrower fixes policy for the last release of the preceding calendar month. Cache layout is internal, and lock formats can migrate on read. A contributor with a newer tool can therefore encounter a different result from release CI. Pin engine and plugins independently. Try upgrades on a disposable checkout with fresh and restored caches. Have someone other than the pilot author reproduce both the upgrade and the previous build. In CI, consume the versioned result format instead of constructing paths inside the cache. [Upstream support and compatibility](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/docs/51-supported-versions.md) · [Result record](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/docs/50-machine-output.md)

**3. Building a CMake dependency in isolation changes what it exports.** The plugin consumes an installed prefix. Hermes sets `ENET_NO_INSTALL=ON` and currently links the ENet target from its vendored CMake tree. Simply passing those same arguments to the plugin does not supply an installed ENet library. For PyroWave, inspect whether the generated `.pc` file embeds an absolute build prefix. The plugin deliberately declines to cache some non-relocatable installs. Rebuild after moving the checkout, then after replacing an SDK at the same absolute path. Compare the linked library and the cache diagnostics. Start with PyroWave's existing install contract and leave ENet in its current build until there is a justified consumer contract. [Hermes vendored targets](https://github.com/MrOz59/Hermes/blob/c1230419254ae191c9f95e03b031dc420742b678/cmake/dependencies/common.cmake) · [Plugin cache and relocation rules](https://github.com/mcpp-community/mcpp-plugins/blob/v0.26.1/docs/deps.md)

**4. An exit code can hide a different test suite.** mcpp discovers each matching C++ test file as a separate program by default and offers grouped modes. Hermes combines sources into one GoogleTest binary, excludes helper files, copies fixtures, and invokes it under Xvfb or with a Wayland filter. One fixture even reads a staged copy of `src/config.cpp`. Compare GoogleTest's case list, executed/skipped counts, fixtures and helper binaries against the reference. On the private audio leg, reproduce its explicit environment setting. Keep the current full-suite invocation until both runners exercise the same cases. [mcpp discovery and grouping](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/docs/08-testing.md) · [Hermes test target](https://github.com/MrOz59/Hermes/blob/c1230419254ae191c9f95e03b031dc420742b678/tests/CMakeLists.txt) · [Private audio workflow](https://github.com/MrOz59/Hermes/blob/main/.github/workflows/isolated-audio.yml)

**5. A valid DEB or RPM can install a different product.** The official plugins put a staged application under `/opt/<name>` and add a launcher in `/usr/bin`. Hermes installs its ELF executable at `/usr/bin/hermes` and its private codec in a distro-specific libdir. Services, file capabilities and crash diagnostics depend on which file actually runs. Initially let mcpp compile and pass the result through an experimental staging adapter into the existing distro recipes. Inspect the installed ELF, capability target, private library, units, upgrades from the previous package and, on Arch, the matching debug symbols. This leaves open a valuable outcome in which mcpp builds Hermes and distribution tools own installation. [Plugin installation layout](https://github.com/mcpp-community/mcpp-plugins/blob/v0.26.1/docs/dist.md#dist-deb-and-dist-rpm) · [Hermes staging](https://github.com/MrOz59/Hermes/blob/main/packaging/linux/stage-install.sh) · [Installed loader test](https://github.com/MrOz59/Hermes/blob/main/scripts/tests/package-loader-smoke.sh) · [Arch debug packaging](https://github.com/MrOz59/Hermes/blob/main/PKGBUILD)

**6. The package runner and the target GPU have different jobs.** mcpp's CUDA rule provides a useful starting point. Hermes must produce its multi-architecture device code on a runner without an NVIDIA GPU, keep NVCC's GCC 14 separate from the ordinary host compiler and ship a binary that resolves distro graphics libraries. Qualification has two parts. Compare the device compiler invocation, generated architecture set and host link on the runner. Then use a matching physical card to encode the first frame and exercise reconnect. An upstream Clang CUDA demo, an NVCC compile and a working NVENC stream each establish different facts. [Upstream CUDA example](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/examples/09-heterogeneous/cuda/README.md) · [Hermes CUDA build](https://github.com/MrOz59/Hermes/blob/c1230419254ae191c9f95e03b031dc420742b678/cmake/compile_definitions/linux.cmake) · [Reference package jobs](https://github.com/MrOz59/Hermes/blob/main/.github/workflows/build.yml)

**7. Two build descriptions can silently enable different features.** For example, Hermes checks the installed KDE screencast XML version before generating C bindings and registering C++ adapters in the host and tests. Both builds can succeed even if only one includes the detached-session helper. For each comparison, record the detected protocol, generated outputs, host/test definitions, helpers and package contents. Try protocol v6 or newer and a configuration where the optional path is unavailable. Share source and expected feature outcomes. If maintaining duplicate detection rules becomes the dominant cost, keep mcpp scoped to the component where it earns its place. [Hermes KWin build and source registration](https://github.com/MrOz59/Hermes/blob/c1230419254ae191c9f95e03b031dc420742b678/cmake/kwin_session.cmake) · [Package validation plan](validation-plan.md)

## How to choose after the trial

| Evidence from Hermes | Decision it supports |
| --- | --- |
| mcpp improves setup or edit/test time for routing, while package qualification remains expensive. | Keep an opt-in mcpp contributor workflow with a maintainer. CMake continues to build release packages. |
| mcpp compiles the host reproducibly and the existing distro recipes pass install, upgrade and runtime checks. | Consider mcpp as the host frontend. Decide separately whether changing package generation improves anything for users or packagers. |
| Most of the benefit comes from isolating the target and sharing configure options. | Keep the extraction and use the focused CMake target or a preset. Document the measured result so a later mcpp release can be reconsidered. |
| System dependency discovery or custom generation dominates the port, and maintainers want a Lua-based native builder. | Try native Xmake on the same troublesome target, with the same distro and comparison criteria. A third permanent manifest would need a distinct benefit and an owner. [Three-tool comparison](build-system-review.md) |

Usman's proposal gets the first opportunity to demonstrate value. The [implementation sequence](implementation-sequence.md) delivers useful changes even if the experiment ends after routing.
