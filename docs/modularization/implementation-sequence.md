# Implementation sequence for Hermes modularization

**Proposed work order, 21 November 2026.** Start with the value returned by session routing, then separate capability decisions from hardware discovery. Work on ownership transfer only after a test can observe cleanup. Run the first mcpp experiment on the extracted routing component. That gives the reviewer separate evidence for the cost of changing the routing rules and the cost of building them.

The source reference for this plan is [workstream commit 24f68ce](https://github.com/MrOz59/Hermes/tree/24f68ce730780a7fab5a9b1cc4b08a6f981ae554). Its [Build Hermes workflow succeeded](https://github.com/MrOz59/Hermes/actions/runs/44868686331) using the existing build. All changes and trials below are proposals. The [branch inventory](baseline.md) and [ownership review](architecture-review.md) describe the implementation that exists today.

## Next boundaries, in dependency order

### 1. Separate capability policy from live probes

Start with `video::choose_capture_readiness_mode`. Its four boolean inputs select a codec/mode or return no safe combination. Exercise SDR fallback, HEVC preference when both HDR codecs are available, AV1 fallback, and refusal when the client/output combination is unsafe. Keep encoder probing, last-result storage, logging and HTTP diagnostics with their present owners. A focused test should run without constructing an encoder. Verify the full host still calls the decision with the same observed capabilities. [Decision and probe caller](https://github.com/MrOz59/Hermes/blob/main/src/video.cpp) · [Existing mode cases](https://github.com/MrOz59/Hermes/blob/main/tests/unit/test_video.cpp)

Next consider `VDISPLAY::assessSession(const SessionFacts&)`. The code already separates collecting compositor/driver facts from producing feature reports, although both live in the large virtual-display translation unit. Move the decision with the types that its callers actually need. Keep `probeSessionFacts` and all device access Linux-specific. Reuse the synthetic KWin, Mutter, wlroots and Hyprland cases. Compare feature IDs, readiness, explanations and remediation text because they reach diagnostics. A protocol being present in a fixture establishes policy behavior. It takes a live session to establish that a compositor actually drives an output. [Facts and report types](https://github.com/MrOz59/Hermes/blob/main/src/platform/linux/virtual_display.h) · [Probe and assessment](https://github.com/MrOz59/Hermes/blob/main/src/platform/linux/virtual_display.cpp) · [Assessment cases](https://github.com/MrOz59/Hermes/blob/main/tests/unit/platform/test_virtual_display_assessment.cpp)

### 2. Characterize pending launch ownership before changing it

A pending launch can expire, lose a cancellation race, collide with another pending launch, or hand a display over to an active stream. Write a deterministic test around these transitions before moving the cleanup code. Observe the identity of the resource released, the operation performed and how often it runs. Keep the existing locking order. [RTSP lifecycle](https://github.com/MrOz59/Hermes/blob/main/src/rtsp.cpp) · [Launch flags and mutex](https://github.com/MrOz59/Hermes/blob/main/src/rtsp.h) · [Stream allocation/destruction](https://github.com/MrOz59/Hermes/blob/main/src/stream.cpp)

| Scenario for the characterization | Observable invariant |
| --- | --- |
| A second launch arrives while one is pending. | Refusal cleans the incoming launch's pending resources. The original launch retains its resources and can still complete. |
| Timeout or successful cancellation wins before ANNOUNCE. | The pending owner releases its resource once. An ANNOUNCE on an already-cancelled launch cannot start it. |
| ANNOUNCE allocates a stream and start subsequently fails. | Allocation has cleared pending cleanup. The stream removal/destruction path deals with the transferred resource. Releasing it a second time from RTSP is a failure. |
| A client disconnects from an isolated session and reconnects. | Where session policy permits resume, disconnect preserves the runtime, its seat and the client's identity. Explicit termination still tears down the correct runtime. |

The first implementation change here should cover one handoff, with enough instrumentation in the test to catch double release. Keep wire response codes, retry timing and the difference between shared displays and isolated runtimes under characterization. Leave registry reorganization for a separate review if the handoff still exposes an ownership problem. [Process teardown](https://github.com/MrOz59/Hermes/blob/main/src/process.cpp) · [HTTPS cancellation](https://github.com/MrOz59/Hermes/blob/main/src/nvhttp.cpp)

### 4. Tackle frame ownership and encoders with hardware evidence

Begin with **one** Hermes-KMS frame on the GPU descriptor path. Trace the producer's sequence, plane FDs, pitches, offsets, modifier, color metadata and sync-file through acquisition, fence handling, import and cleanup. In the current success path the image descriptor receives the plane FDs, the source slots are cleared, and closing the frame releases the fence and any surplus FDs. Compare that with timeout, failed fence and rejected layout. A proposed owner must preserve all of those outcomes, including recycling, without adding a wait, allocation or copy per frame. [Frame contract](https://github.com/MrOz59/Hermes/blob/main/src/platform/linux/virtual_display.h) · [Descriptor transfer and error paths](https://github.com/MrOz59/Hermes/blob/main/src/platform/linux/kmsgrab.cpp)

Test a known Hermes-KMS/AMD VAAPI setup first if available. Repeat on another compositor on the same machine before changing distros, then qualify Intel VAAPI, NVIDIA NVENC and the EVDI/software paths affected by the change. Keep the codec, scene, mode and driver fixed for each before/after pair. Record unsupported and untested combinations individually. A successful software fallback can keep a stream playable while hiding a GPU import regression, so record the selected encoder and actual transfer path. [Compatibility record](../compatibility.md) · [Encoder orchestration](https://github.com/MrOz59/Hermes/blob/main/src/video.cpp)

Use the existing `/api/metrics` rolling capture-to-encode and encode averages and frame/drop counters as a first comparison. Those averages cannot establish p95/p99 or zero-copy. Use a per-frame trace for tail latency and import/copy evidence for the path taken, or mark those measurements unavailable. For a sensitive change, also exercise repeated stop/resume and check for growth in open FDs and memory. [Published metric fields](https://github.com/MrOz59/Hermes/blob/main/src/video.h) · [Metrics handler](https://github.com/MrOz59/Hermes/blob/main/src/confighttp.cpp)

## How a change lands

- **Architectural changes.** Compare the target base immediately before integration. Record the caller that lost a dependency, the owner of the resource, and the test that would fail if the old mistake returned. Bring back one self-contained change at a time. A changing release branch is a reason to re-run characterization, especially for routing and display layouts.
- **Language and tool changes.** Trial one compiler or language feature at a time on a target that benefits. Retain C++23 for the initial host pilot and the existing standards of helpers and CUDA. If a C++26 feature or newer toolchain solves a named problem, compare it in its own experiment. A reviewer should be able to accept the extracted component while deferring that toolchain choice.
- **Adoption and rollback.** Scope the result explicitly to contributor builds, host compilation, or shipped packages. Record the tested revision, maintainer willing to support it, open distro/hardware gaps and how to reproduce the reference build. Keep the shared production source and tests when retiring an experimental manifest. Qualify a release-tool switch through the [package and runtime plan](validation-plan.md) before retiring the reference path.

For the next review, the smallest useful deliverable is the routing characterization, including the integration base's `primary` expectation. Its result gives both the architecture work and Usman's build proposal the same starting point.
