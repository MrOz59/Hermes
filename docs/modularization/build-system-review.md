# CMake, mcpp, and Xmake for the Hermes host

**Decision status · proposed, 21 November 2026.** Keep CMake as the production build and packaging reference. Give **mcpp the first alternative-tool pilot** on a dependency-light Hermes component. Use **Xmake's native builder** as a second comparison if the maintainers want to test the value of a single frontend with distribution-provided dependencies. No tool migration, new minimum version, or C++26 requirement has been adopted. [Hermes source revision](https://github.com/MrOz59/Hermes/tree/c1230419254ae191c9f95e03b031dc420742b678) · [Pilot and decision criteria](validation-plan.md)

The case for mcpp is strongest for a contributor starting with an empty machine who wants a reproducible compiler, module dependencies, and useful incremental builds. A distribution packager needs to install a host binary with Linux file capabilities and a private codec into an existing system. The tools make different promises to those two users.

## Three tools against those requirements

| Criterion | CMake 4.5.x with Ninja | mcpp v2026.11.20.1 | Xmake v3.1.2 |
| --- | --- | --- | --- |
| Contributor entry point | Configure and build are separate. Shared presets could encode common choices. Existing scripts still provision SDKs and distribution libraries. | `mcpp new hello`, `mcpp build`, `mcpp test`. Managed tooling and dependency resolution reduce manual setup. First use can download payloads. | Lua targets, a native build command and integrated package discovery. Can use system libraries or fetch/build configured packages. |
| Who schedules work | CMake drives dependency scanning and generates the Ninja graph. | mcpp owns planning and emits Ninja build files. Ninja is still the underlying executor. | Native Xmake schedules work itself. A separate project exporter generates Ninja files. |
| Modules | `FILE_SET CXX_MODULES` and per-target scanning. Kitware documents the compiler/generator combinations. | Module-first manifests, dependency scanning and BMI cache fingerprints. Self-hosting and published workloads give it a credible pilot. | Native module rules include compiler-specific scanning/building, partitions and fallback-scanner policies. Evaluate the native graph first. |
| Linux dependencies | Current Hermes rules already encode exact/system/fetched dependencies and install semantics. | Lockfile, managed compilers, host/payload `pkg-config` views and custom build actions. The distro sysroot, pinned PyroWave SDK and NVCC host selection need a Hermes trial. | System-only requirements and the `pkgconfig::` provider suit a distro-first policy. Package locking is available for remote recipes. Hermes-specific discovery still needs translation. |
| CUDA and generated outputs | Already represented on the branch. 4.5.x itself has no recorded Hermes trial in this review. | Upstream has a CUDA rule and a real-device example, plus declared actions for generated outputs. Verify NVCC, cross-generation on a GPU-less package runner, and staged output. | CUDA flags/architecture controls and Lua rules exist. Verify the actual NVCC invocation, XML dependency edges and compiled feature set. |
| Packaging and maintenance | Existing package scripts, CI, contributor familiarity and an observed successful branch run. Cost is spread across CMake, scripts and distro recipes. | `mcpp pack` supports multiple runtime layouts. A second manifest would need a named owner while host and package parity are evaluated. | XPack offers DEB/RPM and other formats. Reuse of existing distro recipes is also possible. Both approaches require validating what is installed. |

### CMake and the effective toolchain floor

Named modules entered C++ in C++20. The standard library modules `std` and `std.compat` are a separate C++23 facility. Whether a build works depends on the compiler, scanner, standard library, generator, and the distribution's installation of those components. Selecting C++26 can enable a specific newer language feature, but does not install a scanner, generate missing library metadata or select the right generator. [GCC modules manual](https://gcc.gnu.org/onlinedocs/gcc/C_002b_002b-Modules.html) · [Standard library module proposal](https://www.open-std.org/JTC1/SC22/WG21/docs/papers/2022/p2465r3.pdf)

| Question for Hermes on Linux | What the documentation and checkout establish |
| --- | --- |
| Earliest conventional CMake path for named modules | CMake 3.28 added supported module file sets. For Ninja, the current manual lists Ninja ≥1.11, GCC ≥14 or LLVM/Clang ≥16 for scanning. With Clang, ensure a matching `clang-scan-deps` is available. `CMP0155` affects default scanning of C++20+ sources. Keep scanning scoped to the pilot and its importers. [3.28 manual](https://cmake.org/cmake/help/v3.28/manual/cmake-cxxmodules.7.html) · [4.5 manual](https://cmake.org/cmake/help/v4.5/manual/cmake-cxxmodules.7.html) · [Clang scanner](https://clang.llvm.org/docs/StandardCPlusPlusModules.html) |
| Does a named module require `import std`? | The pilot can include standard headers in a global module fragment. For `import std` on Linux, Kitware 4.5 documents GCC ≥15 or Clang ≥18.1.2 with supported libc++/libstdc++ installations, using Ninja generators. Kitware also flags broken libstdc++ module metadata on Ubuntu versions before 26.04. CMake 4.5 does not support header units. [Kitware support table and limitations](https://cmake.org/cmake/help/v4.5/manual/cmake-cxxmodules.7.html#import-std-support) |
| Would setting the root minimum to 4.5 work with existing distro packages? | Ubuntu 24.04 lists CMake 3.28.3 and default G++ 13. Ubuntu 26.04 lists CMake 4.2.3. The stock CMake package in each case is below 4.5. Installing GCC 14 for NVCC is a separate action from selecting the ordinary C++ compiler. | Does the declared 3.20 floor prove all dependency paths work there? | The root declares 3.20, but the JSON lookup passes `find_package(... GLOBAL)`, an option introduced in 3.24. A smaller alternative to a full frontend change is to use CMake targets for the extracted responsibility, then evaluate a contributor preset on the oldest intended reader. Presets address repeated configuration choices. They do not provision the PyroWave SDK or replace the distro's package recipe. [CMake presets](https://cmake.org/cmake/help/v4.5/manual/cmake-presets.7.html)

**Interface design for a pilot.** Export the input values and the routing decision. Keep the existing process-facing function defined in its original linkage context. Attaching an existing declaration to a named module can change its mangled name under Clang, and importing a named module does not carry preprocessor macros into its consumers. Keep feature macros at the implementation boundary. When a textual SDK or C header is needed, include it in the appropriate implementation or global module fragment. Compile module artifacts for each compatible configuration and distribute the installed host through the existing package contract. [Clang module ABI, macro and migration guidance](https://clang.llvm.org/docs/StandardCPlusPlusModules.html)

### What mcpp's evidence establishes

The command in the proposal is spelled `mcpp new`. A developer can use that entry point without writing a Ninja file. The tagged implementation contains a Ninja backend, and its toolchain guide explains how first-run downloads and offline operation work. Capture the exact toolchain and index snapshot and pre-populate the required payloads for an offline trial. A successful second build with a warm home directory would conceal that bootstrap cost. [Tagged quick start](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/README.md) · [Ninja backend](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/src/build/ninja_backend.cppm) · [Toolchain guide](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/docs/20-toolchains.md)

Self-hosting demonstrates that mcpp can order and rebuild a substantial modular C++ program. Upstream also names xlings and module libraries such as tinyhttps and imgui-m. Its published self-build comparison used GCC 16.1, three samples, an August mcpp version, CMake 4.4.2 and Xmake 3.1.0. The largest improvements were for touching a central interface or changing a comment. The optimized cold-build column used opt-in scheduling. These results motivate measuring identical edits on Hermes, whose graph also contains legacy headers, C, device code, generated protocols and a Web UI. [Projects and benchmark](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/README.md) · [Upstream benchmark data](https://github.com/mcpp-community/mcpp/tree/v2026.11.20.1/bench/results/standard-20260814-linux-x86_64)

Two upstream implementation details make the next experiment more precise:

- **CUDA.** The tagged example builds a SAXPY kernel with a selectable CPU fallback. Its authors report running it on an RTX 4080 via Clang. They also describe why they could not exercise the NVCC route on that machine. Hermes ships NVCC-built device code for multiple architectures from a runner that does not need a GPU. Reproduce that combination before assigning package readiness. [CUDA example and reported hardware](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/examples/09-heterogeneous/cuda/README.md)
- **System integration.** A `build.mcpp` program can declare generated outputs and distinguish host `pkg-config` metadata from the managed payload view. This is a plausible integration route for Wayland and PyroWave. Inspect the selected `.pc` files, compile/link flags and installed loader path on each packaging distro. Pick an explicit packaging mode because the choice controls which runtime libraries travel with the executable. [Build program](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/docs/30-build-mcpp.md) · [Packaging modes](https://github.com/mcpp-community/mcpp/blob/v2026.11.20.1/docs/10-pack-and-release.md)

### What Xmake's evidence establishes

Xmake can build directly, use Lua-based dependency and generation rules, and resolve installed libraries through `pkg-config`. It has module-specific scanner and builder rules. Its package manager offers a dependency lock, and XPack can emit native formats. Those features make Xmake worth evaluating if conventional system-library integration or Lua rules are the main attraction. A full port still has to represent Hermes's optional KWin protocol gate and its package-specific install decisions. [Modules](https://xmake.io/examples/cpp/cxx-modules.html) · [System packages](https://xmake.io/guide/package-management/using-system-packages.html) · [Third-party providers](https://xmake.io/guide/package-management/using-third-party-packages.html) · [Dependency locking](https://xmake.io/guide/package-management/using-official-packages.html) · [Packaging](https://xmake.io/guide/package-management/distribute-private-libraries.html) · [CUDA target options](https://xmake.io/api/description/project-target.html#add-cugencodes)

Treat `xmake project -k ninja` as a separate compatibility question. In tag v3.1.2, the Ninja exporter's source-batch filter lists ordinary C/C++ and CUDA compilation, among others. The dedicated `c++.build.modules` rules are absent from that list. Native module support is documented. A generated Ninja build that survives a clean parallel compile and changes to imports needs its own demonstration if maintainers want that mode. [Native module rules](https://github.com/xmake-io/xmake/blob/v3.1.2/xmake/rules/c%2B%2B/modules/xmake.lua) · [Exporter filter](https://github.com/xmake-io/xmake/blob/v3.1.2/xmake/plugins/project/ninja/build_ninja.lua#L35-L44) · [Project generator](https://xmake.io/guide/extensions/builtin-plugins.html)

## What would change the recommendation

Advance mcpp if it can compile the **same** component with a header consumer and a module consumer, reproduce the targeted invalidation and contributor benefits, and then produce one representative native package with the expected CUDA and private loader behavior. Advance Xmake if its native rules produce that result with materially less custom integration or less long-term maintenance. If CMake plus a narrow target or preset delivers the desired workflow at lower cost, retain it. A production switch would also require coverage of the remaining package matrix and a maintainer willing to own the replacement. The [validation plan](validation-plan.md) specifies how to reach each decision independently.
